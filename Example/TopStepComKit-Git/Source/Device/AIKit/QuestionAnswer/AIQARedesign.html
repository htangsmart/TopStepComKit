DESIGN RATIONALE

一个页面，两条入口，一套状态语言

为什么不放进 Voice Chat？ 协议注释明确 Q&A 是「单次、文本进文本出、独立于 Assistant 会话」的任务。把它塞进 Chat 会混淆 TSAIFeatureAIChat 与 TSAIFeatureQuestionAnswering 两个能力位，测试时无法分辨是哪条链路。所以在根页新增独立 section，协议名直接露出。

为什么用分段控件而不是两个卡片？ 两条入口共用 TSAIQuestionAnswerConfig（agentId），差异只在输入方式和音频路由。文字模式底部是输入框，设备模式底部是录音启停键 + 音频路由；一次录音只生成一个问题。

回答卡片 = 一次 task 的完整生命周期。 头部 badge 跟随 start → partial → completion 三个回调变化；底部只保留耗时与字数，请求 ID 收进日志，避免调试字段打断阅读。deltaText 用渐隐高亮，让「流式」肉眼可见。

取消是逻辑取消。 接口说明当前服务没有物理取消，本地会以 error 终态回调一次。因此发送键变停止键时，composer 上方只提示「正在生成 · 点击停止可取消」，卡片终态用用户能理解的「已停止本次回答」，详细回调留在日志。

设备模式的文字与播放分离。 事件 phase 只描述文字链路、不等待播放；TTS 走 App 注册的 OutputSink。所以轮次卡片里「回答」段落与「播放条」是两个独立区块，Completed 之后播放条可能仍在推进——这正是接口契约。

状态机 · 文字问答

idle→answering→done
answering→failed/cancelled

状态机 · 设备语音问答

未启动→已就绪→Question→Answer→Completed
任一阶段→Failed/Cancelled；stop→未启动
