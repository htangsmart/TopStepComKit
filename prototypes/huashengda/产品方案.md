# 华盛达 Demo · 产品方案

> 版本：v0.3（评审修订） · 2026-09-22
> 配套原型：同目录 `index.html`（单文件，直接双击打开；所有设备数据与蓝牙调用均为模拟）
> 依据：`Docs/Features/Huashengda/{plan, protocol-extract, test-cases, verification, manifest}`、`TSHuashengdaInterface.h`、`TSHsd*Model.h`、`TSHsdDefines.h`、`TSNpkHuashengda.m`（参数校验与错误行为），以及 Example 工程现有的 `TSDeviceMenuBuilder` / `TSBaseVC` / `TSPeripheralLockVC`。
> 范围：华盛达包 bit28–34 共 7 项。闹钟类型（bit27）与表盘槽位已是公版能力，不在本方案内（见 §4.8 / §4.9 的指针）。

## 0. 一页结论

华盛达这一包能力本质上是一块**儿童手表的家长端**：管住（家长模式、课堂模式）、带好（任务&奖励、习惯）、看见（使用统计、游戏）、兜底（ICE）。Demo 按这个心智分组，而不是按指令码 0x59–0x67 的顺序平铺。

Demo 同时要服务三类人，所以它不只是"能点通"：

| 使用者 | 他要完成的事 | Demo 给他的东西 |
|---|---|---|
| 客户 App 开发 | 看懂每个接口怎么调、参数边界在哪 | 每页右上角「接口日志」、字节计数器、整表覆盖的显式确认 |
| 测试 / 固件 | 跑完 `test-cases.md` 第 4 节里属于本包的约 31 条真机用例（4.1–4.4、4.7；闹钟类型 4.5 与槽位 4.6 归公版页） | 「保存 → 自动回读 → 字段级比对」、原始能力位、日期来源徽标、空天占位的可视化 |
| 你自己 / 客户演示 | 一眼看到 SDK 已经覆盖了什么 | 能力总览卡 + 四组功能入口，不支持的能力置灰并写明 bit 位 |

落地范围：**1 个菜单入口 + 1 个总览页 + 7 个功能页**。P0 约 8.5 人日，P1 验证增强约 1.5 人日。

`verification.md` 偏差 2 里写的"未新增 Demo 入口"，由本方案补齐。

## 1. 设计原则

**按家长的心智分组，按协议的事实说话。** 分组用人话（管控 / 成长 / 洞察 / 安全），但每个入口的副标题都带上能力位与指令范围，开发者不用回头翻文档。

**设备是唯一事实来源。** 进页面先读；改完显式「保存到手表」；保存成功后自动再读一次并比对。协议没有变更通知（D-16），所以每页都支持下拉刷新，并在底栏显示"上次同步时间"。

**协议的坑要做成界面，而不是写在注释里。** 整表覆盖、UTF-8 字节上限、`count` 是累计值、日期可能是推算的、ICE 和排名趋势读不回来——这些都直接出现在对应页面上。

**不支持 ≠ 隐藏。** 总览页 7 个能力位（bit28–34）全部展示，不支持的变成虚线占位卡并标注 `bit N 未置位`，点击弹一条说明。只要 `comKit.huashengda` 非 nil（即 NPK 设备）就允许进入总览，哪怕 7 项全未置位——D-02 要在这种设备上发起调用看 NOTSUPPORT，边界测试工具也在总览里。菜单只在 facade 为 nil（非 NPK）时置灰。

**简洁，但不简单。** v0.1 直接套了系统设置页的样子（灰底白列表、系统蓝、文字符号当图标），那是偷懒，v0.2 整体重做：自有一套色彩与组件（见 §3.8），每页一个色相，信息尽量用图形说话——时间段用 24 小时时间轴、习惯用进度环、ICE 与任务用手表实时预览、空态与错误用统一的插画组件。任何地方都不再用文字符号或 emoji 充当界面图标。

## 2. 信息架构

```
设备 Tab（TSDeviceMenuBuilder · featureItems）
└─ 华盛达定制  ← 新增菜单项；enabled = ready && sdk.huashengda != nil；副标题按 isSupport 变化
   └─ TSHuashengdaVC（总览）
      ├─ 能力总览卡        bit28–34 × 7，附 originAbility 原始 16 字节
      ├─ 管控
      │   ├─ 家长模式      TSHsdParentalModeVC      bit29 · 0x5A/0x5B
      │   └─ 课堂模式      TSHsdClassroomModeVC     bit30 · 0x5C/0x5D
      ├─ 成长
      │   ├─ 任务与奖励    TSHsdTaskVC → TSHsdTaskEditorVC     bit31 · 0x5E/0x5F/0x60
      │   └─ 习惯          TSHsdHabitVC → TSHsdHabitEditorVC   bit32 · 0x61/0x62
      ├─ 洞察
      │   ├─ 使用统计      TSHsdUsageVC             bit33 · 0x63/0x64/0x65
      │   └─ 游戏          TSHsdGameVC              bit34 · 0x66/0x67
      ├─ 安全
      │   └─ ICE 紧急标签  TSHsdIceVC               bit28 · 0x59
      └─ 边界测试工具（P1）
```

不在本方案内、已另行处理的公版改动：闹钟类型（`TSAlarmClockVC` / `TSAlarmEditorVC` / `TSAlarmTypePickerVC`，已写好待编译）、表盘槽位（表盘管理原型）。

为什么是一个入口而不是 7 个菜单项：`featureItems` 已经 20 项，华盛达是客户定制包，平铺会淹没公版能力；而且 `comKit.huashengda` 在非 NPK 下为 nil，一个入口统一判空最干净。菜单项就是在 `TSDeviceMenuBuilder.featureItems` 里加一条 `vcName = @"TSHuashengdaVC"`，`TSViewController` 反射 push，不需要改 `TSViewController`。

## 3. 通用交互规范

### 3.1 页面生命周期

进入页面即发起读取，四种终态必须区分：

| 状态 | 表现 |
|---|---|
| 加载中 | `TSLoadingHUD`，内容区不出现旧数据 |
| 有数据 | 正常渲染，底栏显示"已与手表同步 · HH:mm" |
| 成功但为空 | `TSEmptyView` + 主操作（如"添加第一个任务"）；使用统计空数组写明"设备暂无统计数据" |
| 失败 | 错误卡：人话原因 + `domain / code` 小字 + 「重试」。不清空已有草稿 |

不支持（`isSupportXxx == NO`）不会走到这里：总览页入口是虚线占位卡，点了只弹说明。

每个有读取的页面右上角有「重新读取」按钮（不做下拉刷新，避免和滚轮、时间轴手势冲突）；有未保存修改时先确认再读，读到的结果覆盖草稿。

### 3.2 保存模型：显式保存 + 自动回读

多字段模型（家长模式、课堂模式、任务、习惯）统一用**底部保存栏**，不做"拨一下开关就发一条蓝牙包"：

1. 任一字段变化 → 底栏出现"有未保存的修改"，主按钮「保存到手表」点亮；
2. 点击保存 → 本地校验（字节数、条数、范围）→ 调 `setXxx:` → HUD；
3. 成功后**立即调 `fetchXxx:` 回读**并与刚才下发的模型逐字段比对；
4. 一致 → toast "已保存，回读一致"；不一致 → 弹「回读差异」面板，列出字段 / 下发值 / 回读值，页面以回读值为准。

第 3、4 步直接对应真机用例里所有 "set → get 一致" 的条目（D-12、D-15、D-20、D-24），测试不需要再手动点一次刷新、肉眼比对。

比对规则：任务、习惯按 `taskId` / `habitId` 对齐，不按数组下标；手表维护的字段（任务 `state`，习惯 `state`、`reachGoalDays`、`maxReachGoalDays`、`latestAchieveGoal*`、`achieveGoalRepeat`）不计入差异——set→get 之间孩子完成了任务不算"不一致"。

有未保存修改时返回上一页，弹"放弃修改？"确认。

### 3.3 整表覆盖要说出来

`setTaskInfo:` 和 `setHabits:` 都是整表下发。保存按钮文案直接写「保存全部 N 项到手表」。确认框只在两种情况出现：任务页每次保存（因为连 `totalCoins` 一起覆盖，见 §4.3 讨论点 A），以及任一页 N = 0 时（"清空手表上的全部任务 / 习惯？"，手表是否真的清空由固件决定，需补真机用例 D-28）。习惯页正常保存不弹确认。

SDK 对 0 条的处理不一致，方案按 SDK 现状：`setHabits:` 与 `setTaskInfo:` 允许 0 条；`setIceLabels:` 与 `setGameRankingTrends:` 对空数组返回 `TSERROR_INVALID_PARAM`，所以 ICE 与排名趋势页在 0 条时禁用发送，不提供"清空"。

### 3.4 只写不读的能力

ICE（0x59）与游戏排名趋势（0x67）协议没有读取指令。页面固定一条说明条："协议无读取指令，以下为 App 本地缓存的上次发送内容"，并显示上次发送时间；发送过的内容允许原样重发（手表重置后需要）。缓存放 `NSUserDefaults`，按 SDK 的 peripheral 标识分 key（iOS 拿不到蓝牙 MAC，用 `TSPeripheral` 的 identifier / 固件回传的 mac 字段），切换设备即失效。

### 3.5 错误文案

| 来源 | 给用户看的话 | 小字 |
|---|---|---|
| `TSERROR_NOTSUPPORT` | 当前设备不支持该能力 | `huashengda / NOTSUPPORT` |
| `TSERROR_INVALID_PARAM` | 指出具体字段，如"第 2 个任务的标签超过 32 字节" | 发送前本地已拦截，正常不会出现 |
| `eTSErrorDataSetFailed` | 手表拒绝了这次设置 | 多包时附失败包序号（`userInfo`） |
| `missing some fragments` | 手表返回的分包不连续，可能跳过了没有使用记录的日期 | 指向 D-31，提示反馈固件。注意这是 BleMeta 的描述文本不是 code，OC 里只能按 `localizedDescription` 包含判断，建议 SDK 补一个专用 code |
| 断连 / 超时 | 与手表的连接已断开 / 手表没有响应 | 原 error 透传 |

错误码在 OC 里是整数，小字里的 `code` 名称由 `TSHsdErrorText`（§5 Common）做 code → 名称映射。

### 3.6 线程与断连

SDK 承诺 HSD 回调在主线程，但 CLAUDE.md §25.2 是工程硬约束，Demo 里仍统一 `dispatch_async(main)` 再刷 UI，给客户一个不会错的示范。断连时页面保留已读数据与草稿，保存按钮置灰并提示"未连接"；重连后（监听 SDK 连接状态回调）恢复保存按钮，不自动重读，由用户点「重新读取」——否则会覆盖草稿。App 进后台再回前台不自动刷新；保存过程中进后台，等回调完成或明确失败（D-62）。

### 3.7 接口日志（P1）

每个华盛达页面右上角一个终端图标按钮（最近一次调用失败时带红点），打开当前会话的调用记录：方法名、参数摘要、结果、耗时。实现是一个 `TSHsdCallLog` 单例 + 一个列表页，所有页面经由它转调 SDK。对开发者这是"活文档"，对测试这是不接电脑也能看的抓包摘要。

### 3.8 视觉与组件规范（v0.2）

**色彩。** 中性色带一点靛蓝偏色，不用纯灰；主按钮统一用墨色（深色模式反相为近白），彩色只留给"身份"和"状态"。

每个页面只设一个 `--hue`，开关、星期键、时间胶囊、进度、条形全部跟随它；落到 OC 就是 `TSBaseVC` 子类上的一个 `tintColor`。

**字体。** 系统字体；数字（金币、统计、时间、得分）用 SF Pro Rounded（`UIFontDescriptorSystemDesignRounded`，iOS 13+，iOS 12 回退到系统字体），等宽只用于 bit 位、指令码与日志。页面用大标题（`prefersLargeTitles`），标题下一行小标签写能力位与指令码。

**形状与层级。** 卡片圆角 22、图标块 13、按钮全圆角；阴影只有两级（卡片 / 浮起），分隔线只在卡片内部且左右缩进。图标块用"12% 色相底 + 色相描边图标"，不用实心彩块。

**图标。** 统一 24 栅格、1.75 描边、圆头；正式工程用 SF Symbols 对应项（`checklist`、`leaf`、`chart.bar`、`gamecontroller`、`heart.text.square`、`terminal` 等）。工程最低版本 iOS 12.0 而 SF Symbols 需要 iOS 13，需要二选一：把 Deployment Target 提到 13（建议，工程里已有多处 `UITableViewStyleInsetGrouped` 等 13+ API），或给 26 个界面图标准备 PNG 回退。任务类型 / 游戏 / 应用这三张枚举表（共 96 项）属于**内容**而非界面图标，原型里暂用 emoji 占位，正式版建议向华盛达要手表固件里的同款图标资源。

**本地化。** 除页面文案外还有内容枚举：游戏 25、应用 48、习惯类型 4 + 状态 6（任务类型复用闹钟页的 `alarm.type.*`），约 85 个键 × 3 语言。印地语按 UTF-8 一个字符 3 字节，32 字节只能放约 10 个字符，字节计数器旁的提示要按语言给出可输入字符数的参考。

**组件清单。** 深色设备卡（7 段能力条：支持绿实心、不支持虚线框，带短名，可展开）、Bento 功能卡（带实时摘要）、24 小时时间轴、时间对、星期键、字节进度线输入框、进度环、手表预览、排序条形、空态插画（统一构图，换图标与色相）、浮动保存条、底部面板、确认框、顶部胶囊提示。

**浮动保存条。** 没有修改时页面底部只有一枚内嵌的"已与手表同步 · HH:mm"小标；出现修改才从底部浮起保存条（左侧状态、右侧墨色按钮）。只写能力（ICE、排名趋势）的保存条左侧固定写"只写能力 · 上次发送时间"。

## 4. 各页面方案

### 4.1 总览 `TSHuashengdaVC`

顶部是一张深色**设备卡**，页面的视觉重心：设备名、连接状态、一行 7 段能力条与"7 / 7 项定制能力可用"。点"能力位"展开 bit28–34 明细与 `originAbility` 原始字节（D-01），默认收起——摘要先于细节。bit27（闹钟类型）已是公版能力，不再计入。

下面按四组排成 2 列 **Bento 卡片**，每张卡直接显示手表上的当前状态：家长模式"已开启 · 游戏 18:00–20:00"、课堂模式"工作日 08:00–16:30"、任务"4 个任务 · 30 金币"、习惯"3 个习惯 · 2 个进行中"。为此进入总览时会顺序读取这 4 个轻量接口（加载中显示骨架条，读过的不重复读，某个失败只影响那一张卡）；使用统计是多包列表、ICE 与排名趋势读不回来，这三张卡只显示说明或本地缓存。不支持的能力变成虚线占位卡并写明"bit N 未置位"，不隐藏；点击弹一条说明（"SDK 会直接回调 TSERROR_NOTSUPPORT"）。能力位展开区里另加一行灰色的 `bit27 闹钟类型 · 公版能力，见闹钟页`，不计入 7 项，方便测试对照 D-01 的原始字节。

接口：7 个 `isSupportXxx`（ICE … 游戏）、`featureAbility.originAbility`、`fetchParentalMode:` / `fetchClassroomMode:` / `fetchTaskInfo:` / `fetchHabits:`（摘要）。

### 4.2 家长模式 / 课堂模式

两页同构：一张主开关卡 + 一组明细，主开关关闭时明细折叠（值保留，不清零）。时段统一用 **24 小时时间轴**表达：轨道上高亮允许 / 静默的区间，右上角直接给出时长（如「每天可玩 2 小时」）；跨天时自动拆成两段。时间轴下面是并排的「开始 / 结束」时间对。

家长模式明细：允许设置时间、允许进入设置、允许设置闹钟三个开关；「限制游戏时段」开关 + 展开的开始/结束时间。结束早于开始时在时间行尾标"次日"，不拦截（D-14 要求透传）。

课堂模式明细：开始/结束时间 + 周一到周日 7 个圆形日期键（bit0=周一，复用 `TSAlarmRepeat`），下方三个快捷键「工作日」「每天」「周末」。开启但一天都没选时给黄色提示"未选择重复日，手表行为以固件为准"，不拦截。

> ⚠ 极性待真机确认：proto 注释只写"时间设置开关"，SDK 头文件解释为"允许在手表上设置时间"，而 `gameDurationEnabled` 是"是否限制"。三个"允许"与一个"限制"极性相反，Demo 文案先按 SDK 头文件写，D-12 执行时请顺手确认，错了只需改文案。

接口：`fetchParentalMode:` / `setParentalMode:completion:`，`fetchClassroomMode:` / `setClassroomMode:completion:`。覆盖 D-12–D-16、D-60。

### 4.3 任务与奖励

**金币卡**（顶部）：大号 `totalCoins`，右侧「兑换奖励」；下面两格「今日任务完成 n / m」「今天还能赚 X 金币」，只统计启用且重复日包含今天（或仅一次）的任务。兑换前确认；回调 `success` 为 NO 时明确提示"手表返回兑换失败"而不是当作错误；无论成功与否都重新 `fetchTaskInfo:`，让测试看到金币怎么变（D-23 的"归零还是减少"由固件定）；兑换成功但回读失败时提示"兑换已完成，但回读失败"，不能误报成兑换失败。金币数字可点开手动调整——因为 `setTaskInfo:` 本来就会下发它。

待固件确认的三个假设（原型里都按假设做了，正式版前要核）：标签留空时手表显示什么；`taskId` / `habitId` 由 App 从 1 起分配是否可行；0 金币时兑换是否返回 `success = NO`。

**任务列表**：标题带计数 `3 / 5`。每行：类型图标块、标签、时间（`timeEnabled == NO` 显示"不显示时间"）、重复、`+N` 金币、状态徽标（未开始 / 进行中 / 已完成，只读）、启用开关。满 5 条时「添加」置灰并写"已达上限 5"。删除在编辑页底部（不做左滑，避免和编辑模式冲突）。

**编辑页**：类型（复用闹钟页的 `TSAlarmTypePickerVC`，`TSHsdTaskType = TSAlarmType`；页脚注"取值待固件确认，SDK 透传"）、标签（右侧实时 `n / 32 字节`，超限变红并禁用保存）、描述（`n / 100 字节`）、「在手表上显示时间」开关 + 时间、重复、金币步进器、启用。`taskId` 由 App 分配（现有最大值 + 1），编辑页只读展示。`state` 不可编辑，保存时原值带回。

接口：`fetchTaskInfo:` / `setTaskInfo:completion:` / `exchangeTaskReward:`。覆盖 D-20–D-23、D-27。

> **讨论点 A：totalCoins 的陈旧覆盖。** 孩子在手表上刚完成任务、金币 +5，家长此时在 App 里改了一个任务标签并保存，App 手里的旧 `totalCoins` 会把这 5 个金币抹掉。Demo 层面我建议：保存前先静默 `fetchTaskInfo:` 一次，如果金币或任务状态与本地快照不同，弹出"手表侧数据已变化"：用户没改过金币就"采用手表数据并保存"；用户自己也改了金币就三选一「用我的 / 用手表的 / 取消」。代价：任务页一次保存 = 静默回读 + 确认 + set + 回读校验，3 次蓝牙往返、最多 2 个弹窗；习惯页没有金币问题，不做静默回读。

### 4.4 习惯

**列表**：标题计数 `n / 10`。每行：类型图标（自定义类型显示 `label`，其余显示类型名）、时间 + 时长、重复、状态徽标（6 种，`Deleted` 置灰保留显示）、进度条 `reachGoalDays / taskDays`、一排 7 个小圆点表示 `achieveGoalRepeat`（过去一周哪几天达成）。

**编辑页**分两组。可编辑：类型（切到预置类型时清空标签，避免隐藏的标签继续参与校验和下发）、标签（仅自定义类型可填，32 字节计数）、时间、时长（分钟）、重复、任务天数、关联功能（无 / 运动）、提醒时长（秒）、提前提醒（分钟）。**设备维护**（只读，灰底）：状态、已达成 / 最大达成天数、最近达成日期、过去一周达成。保存时只读字段原值带回。时长 1–600 分钟、任务天数 1–365、提前提醒 0–120 分钟、提醒时长 0–300 秒是 Demo 约定的输入范围，协议与 SDK 没有上限。

接口：`fetchHabits:` / `setHabits:completion:`。覆盖 D-24–D-27。

> **讨论点 B：** 设备维护字段是否给测试留一个"高级：允许编辑"开关（方便构造 state=Overdue 之类的数据）？我倾向 P1 再加，默认只读。

### 4.5 使用统计

顶部分段「应用 | 游戏」，分别对应 `fetchAppUsage:` / `fetchGameUsage:`，首次切到才加载。

**日期条**：横向一排日期键，`dayOffset` 0 显示"今天"、1 显示"昨天"，其余显示 `M/d`。每个键下有一个小徽标：`设备` 或 `推算`。只要有任何一天是推算，日期条下方出现一条说明："日期由手机时间减去天数偏移推算，手表时间不准或跨时区时可能差一天"（D-31b）。标题旁显示"设备保留 N 天"（D-31c）。

**当天内容**：三个数字（总次数、涉及应用数、最高频应用）+ 按次数降序的横向条形榜。类型名来自 `TSHsdWatchApp` / `TSHsdGameType`，未知取值显示 `未知类型 (N)`。空天显示"这一天没有使用记录"并注明"设备以空包占位"——这正是 D-31 要观察的现象。

**重置**：页面底部危险操作，确认文案写明"是否同时清空应用与游戏两类由固件决定"。成功后**自动重新拉取两个分段**并用 toast 汇报"应用：已清空 / 游戏：仍有 3 天数据"，D-33、D-37 一步出结论。

图表只用条形榜：`count` 是同类可比的计数，排序后的条形是最诚实的形式；不做饼图，不做跨天折线（保留天数太少、且设备随时可能重置）。

接口：`fetchAppUsage:` / `fetchGameUsage:` / `resetUsageStatistics:`。覆盖 D-30–D-33、D-37。

### 4.6 游戏

分段「最高记录 | 排名趋势」。

**最高记录**：25 个游戏的横向选择条，选中即调 `fetchGameTopRecordsWithType:completion:`。结果按设备返回顺序列出（不在 App 侧重排，D-34 要记录实际顺序），每条：名次、得分、等级、时长、日期。空数组显示"这个游戏还没有记录"。

**排名趋势**（只写）：列表编辑，每行 = 游戏 + 排名（0–255）+ 趋势三态（降 / 平 / 升）。一个游戏一条，所以 UI 最多 25 条，`n / 30` 的 30 是协议上限，31 条只在边界工具里构造。0 条时禁用发送（SDK 对空数组返回参数错误）。工具按钮「填充 25 个游戏」一键生成测试数据（D-36）。发送后缓存到本地，顶部同 ICE 的"只写"说明条。

接口：`fetchGameTopRecordsWithType:completion:` / `setGameRankingTrends:completion:`。覆盖 D-34–D-36。

### 4.7 ICE 紧急标签

最多 3 条输入框，每条右侧 `n / 63 字节`。允许 emoji（D-11）。「发送到手表」后显示上次发送时间，可原样重发。"只写"说明条。三行全空时禁用发送：`setIceLabels:` 对空数组返回 `TSERROR_INVALID_PARAM`，协议也没有清空指令，如需"清空"要先和固件确认语义再放宽 SDK 校验。

接口：`setIceLabels:completion:`。覆盖 D-10、D-11。

### 4.8 闹钟类型 → 公版能力（已移出）

`TSAlarmClockInterface.isSupportAlarmType` / `fetchSupportedAlarmTypes:`，枚举 `TSAlarmType`（0–22），`TSHsdTaskType` 为其别名。Example 的 `TSAlarmClockVC` / `TSAlarmEditorVC` / `TSAlarmTypePickerVC` 已写好待编译，真机用例 D-40–D-45 随闹钟页验证。本方案只复用 `TSAlarmTypePickerVC` 与 `TSAlarmTypeDisplay`。

### 4.9 表盘槽位 → 公版能力（已移出）

`dial.isSupportDialSlots` / `fetchDialSlots:`，设计与接口映射在 `prototypes/dial-management/`，真机用例 D-50–D-52c 随表盘页验证。

### 4.10 边界测试工具（P1）

总览页底部一个"边界测试工具"入口，列出预期会被 SDK 在发送前拦截的调用，点一下就发、直接显示拿到的 error：6 个任务（D-21）、11 个习惯（D-25）、33 字节标签（N-06）、4 条 ICE、单条 64 字节 ICE、0 条 ICE（N-12）、ranking=256（N-11）、31 条排名趋势与 0 条趋势（M-16）；并发 0x61 + 0x63（D-61）、连续 20 次家长模式读写（D-60）。这些不该污染正常 UI，但测试确实要跑。

## 7. 需要你拍板的问题

1. **入口形态**：一个「华盛达定制」菜单项进总览页（我的建议），还是拆成若干项平铺进设备菜单？

3. **保存模型**：统一"显式保存 + 自动回读比对"（建议），还是开关类页面改成即拨即发？
4. **讨论点 B**：习惯的设备维护字段默认只读，P1 再给高级编辑开关，可以吗？
5. **P1 的两件事**（接口日志、边界测试工具）要不要提到 P0？如果这版 Demo 的首要任务是跑完 `test-cases.md`，我建议边界工具提前。
6. **家长模式三个开关的极性**需要你或固件确认一句；确认前文案按 SDK 头文件的"允许…"。
7. **菜单名称与图标**：中文「华盛达定制」/ 英文 "Huashengda Kit"；给客户演示时是否需要换成中性名称（如「儿童守护」）？
8. **本地化范围**：工程现有 zh-Hans / en / hi 三份，华盛达页面是否三份都补，还是先中英？
9. **总览页预读**：进入总览顺序读 4 个轻量接口来生成卡片摘要，换来的是「一眼看到手表现状」。如果你担心进页面就发 4 条蓝牙指令，可以退回成只显示静态说明。
10. **内容图标**：任务类型 / 游戏 / 应用共 96 项，原型用 emoji 占位。正式版是向华盛达要固件里的同款图标，还是用 SF Symbols 近似映射？
11. **视觉方向**：v0.2 这套（靛蓝偏色中性底 + 每页一个色相 + 墨色主按钮）只用于华盛达页面，还是你希望以后逐步推广到 Example 其他页面？这决定组件放在 `Device/Huashengda/Common/` 还是 `BaseVC/View/`。
12. **iOS 12**：工程最低版本 12.0，界面图标依赖 SF Symbols（13+）。建议提到 iOS 13；不提就要给 26 个图标做 PNG 回退。
13. **ICE / 排名趋势的清空**：SDK 对空数组返回参数错误，协议无清空指令。要不要向固件确认"下发空列表 = 清空"并放宽 SDK 校验？
14. **0 条任务 / 习惯**：SDK 允许下发空表，手表是否清空未验证，需补真机用例 D-28。
